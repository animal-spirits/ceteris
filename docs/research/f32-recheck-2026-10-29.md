# f32 vs f64 recheck on the Rust core (2026-10-29)

Third check of whether the econ core can drop to f32 (halve memory, enable GPU). Run on `main`
at 98d50b8, branch `claude/project-thread-tl3z0t` (probe, not for merge), patch
`research/f32-probe-2026-10-29.patch`, GPU prototype in `research/f32-gpu-prototype-2026-10-29/`.

## Method

f32 storage is emulated by rounding through f32 (`x as f32 as f64`). Five runs on the fixture
(4 countries, 25 provinces), 4,800 ticks (400 years), each against the f64 baseline:

- kernel nudge: every trade kernel entry and source/dispatch intermediate moved one f64 ulp
  (the f64 noise floor)
- kernel f32: the same values rounded to f32
- state nudge / state f32: every state array (prices, stocks in the ledger, pipeline, wages,
  employment, income, D/Q/sales, profit, price level) nudged or rounded after every tick
- kernel + state f32

Rounding only stored values is optimistic: real f32 arithmetic rounds every operation.

## Results

Max |dlog| for prices, wages and employment; max gap relative to the largest value for stocks.

| run | invariants | price @1200 | price @4800 | stocks @1200 | stocks @2400 | stocks @4800 |
|---|---|---|---|---|---|---|
| kernel nudge (f64 floor) | hold | 2.3e-13 | 1.6e-12 | 8.1e-14 | 7.6e-14 | 1.7e-13 |
| kernel f32 | fail at tick 0 (dispatch mass: 44609884 of 44609886) | 3.5e-8 | 4.7e-8 | 3.2e-7 | 3.4e-7 | 3.5e-7 |
| state nudge (f64 floor) | hold | 4.4e-13 | 1.3e-12 | 1.5e-13 | 2.8e-13 | 5.4e-13 |
| state f32 | hold (see below) | 1.1e-6 | 3.0e-6 | 6.3e-6 | 5.0e-5 | 2.3e-4 |
| kernel + state f32 | fail at tick 0 | 7.7e-7 | 2.4e-6 | 6.5e-6 | 5.2e-5 | 2.3e-4 |

- **Kernel f32** is bounded (no drift; the model contracts prices) but breaks the dispatch mass
  check at tick 0, as on 2026-10-27. It needs an f64 closing pass per origin.
- **State f32 does not stay bounded.** Prices and wages settle near 3e-6, but stocks are
  integrators with no restoring force: their error grows 5 to 8 times per doubling of run length
  (6e-6 at 100 years, 2e-4 at 400). The f64 floor stays at 1e-13.
- State f32 "holds" the invariants only because the ledger opens each tick from the balances
  it finds, so rounding between ticks is invisible to the check. It silently made or destroyed
  7.8e4 units gross (3.6e3 net) of 3.4e10 held over 100 years; the f64 nudge, 6e-3.
- **Range** (ADR 0093): K = tau^-theta underflows f32 above tau ~3.8 at theta 64.85. f32 K is
  only possible as ln K. Origin weights after the per-country shift span 1e-308 in f64 and only
  1e-38 (1e-45 subnormal) in f32, so f32 shrinks the reachable price spread.
- **Calibration**: the Rust calibration solver is not on `main` yet (ADR 0113 step 4d), so not
  run. In-tick solver tolerances on `main` are 1e-12 to 1e-15 (clearing wage 1e-13, income
  1e-15, labour, Leontief, dispatch 1e-12): below f32's 1.2e-7 resolution, so unreachable by
  construction. Rerun once 4d lands only if tolerance loosening is on the table.

## Memory

Full pack, by count (4,796 provinces x 10 goods, 14,388 pops, about 48,000 enterprises, 4
pipeline slots, 356,080 crossings per traded good x 7):

| part | f64 | f32 |
|---|---|---|
| tick state (markets, pipeline, ledger goods, per-enterprise and per-pop vectors) | ~30 MB | ~15 MB |
| crossing kernel entries (32 B -> 20 B) | ~80 MB | ~50 MB |
| peak of a 120-tick run with history (Task 19) | 1.88 GB | ~1.83 GB |

The peak is history, snapshots and build-time data, not tick state. f32 saves about 3% of it.

## Speed

Dispatch-shaped crossing pass (356,080 entries, 2,000 gateways, scattered gathers), this
container's Xeon: f64 0.79 ms, f32 0.74 ms per class pass (6%). Consistent with Task 19: the
pass is latency-bound (dependent sums, divisions), not bandwidth-bound.

## GPU

- WGSL has no f64 at all, so GPU means f32 state or f32 with f64 on the CPU side, and the
  problems above.
- No float atomics in WGSL: the scatter-adds of dispatch must become gathers over a column
  transpose (done in the prototype). That fixes the order on one device.
- Prototype (wgpu 24, Vulkan, crossing pass gathered by destination gateway) on llvmpipe (the
  only adapter here; no hardware GPU): bit-identical to CPU f32 without FMA. The same CPU code
  with FMA contraction differs in 668 of 2,000 outputs by up to 3 ulp. WGSL lets a driver
  contract a*b+c and gives f32 division 2.5 ulp, so a hardware driver that does either breaks
  hashes, replays and forks. One software adapter cannot show cross-vendor identity; a test on
  the Mac's Metal adapter would show one more pair, not a guarantee.
- llvmpipe timing (0.5 ms vs 1.3 ms CPU serial) is not representative of hardware.

## Verdict

Same as 2026-10-27, now with a stronger reason: f64 is needed for state (stocks drift without
bound in f32), for conservation, and for every solver tolerance on `main`. f32 is safe only
for kernel storage (as ln K) with an f64 closing pass, and buys ~30 MB and ~6% on one pass.
GPU stays a statistical-reproducibility ensemble mode at most.
