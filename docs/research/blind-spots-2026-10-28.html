Blocks a 1.0 gate

Design these before the phase that first needs them

1Who sets policy in 1.0
FoundDESIGN 2.4 says that in 1.x "policy comes from estimated reaction functions or the historical policy tape". Neither is designed. 9.6 says budgets "are set by the state AI under institutional rules (Section 10)", and 9.4 makes default "a strategic choice of the state AI", but the Tier 1a planner (12.3) needs coalition weights from P6, which is 2.0. The tape gets one bullet in 15.7: no sources, no format, no lever list.
BlocksP5a (who sets taxes and spending), P5b (who decides to default), P8 (runs to 2150 need policy after the tape ends in 2024), P9 (the hindcast feeds the tape to separate mechanism error from policy error). Steward mode in 1.3 scores the player against this agent.
ProposedA policy-agent ADR and a policy SPEC written before P5a: one rule per lever (Taylor or peg defence from 9.2, a Bohn-type fiscal reaction on debt and the cycle, tariffs and trade wedges held at their last tape value, default as a hazard on debt service and reserves), each with country parameters estimated on 2000 to 2010. The tape lists levers, sources and licences, and the format it shares with the shock tape of 13.1. Card 1.
2Run files, saves and compatibility across versions
FoundFive words for overlapping things: scenario file (0113, 0188), run file (0142, 0143), session file (0132), run store (19.1), snapshot (0002). Replay is bit-exact only for the same engine build and pack hash, yet nothing says what happens when 1.1 opens a run made in 1.0. Pre-P3 B5 makes an old snapshot a DecodeError; 0136 and 0197 promise a ceteris migrate path; 0002 re-blesses everything when snapshots move to Arrow in P3. DESIGN 23.3 calls the pack, scenario and intervention formats "public API" under a versioning policy that lives only in the 23 October roadmap page, not in the repo.
BlocksP3: run hashes and share (0128), the branch store and the Arrow move (0002), the read-only API schema (0197).
ProposedOne file-family ADR: the scenario file (pack hash, engine version, parameters, edits, seeds) is the save and the stable public format; snapshots and the run store are caches keyed by engine version and can be thrown away. A newer engine opens an old run's stored results read-only and offers to re-simulate it as a new, labelled branch. The compatibility promise for 1.x is written into the repo. Card 2.
3History retention and the disk budget
FoundThe econ SPEC measures 1.88 GB peak memory for 120 ticks with history, on 10 goods. 1.0 has 45 goods, runs to 2150 (about 1,800 ticks), and ensembles default to K = 32 (14.1). Taken linearly that is tens of GB per run and terabytes per ensemble. 19.2 budgets memory for one run (6 GB) and says nothing about disk.
BlocksP3 ensembles and fan charts; the P8 run to 2150.
ProposedA retention ADR: full history at the view interval for the live branch only, annual history after a horizon, ensemble members keep declared outcome metrics and snapshots, and anything else is re-simulated on demand (cheap, since replay is exact). A disk budget per run and per ensemble sits beside 19.2. Agent default unless you object.
4Data licences inside shared runs and exports
FoundLicence checks stop at the pack. Snapshots are derived from every source, including ones marked no-redistribution in sources.toml (for example the IFPRI SPAM terms and GADM). ceteris fetch <hash> pulls snapshot chunks "from any mirror or peer" (0128), and 0197 exports tables to Parquet and GeoPackage. Both redistribute derived data with no licence filter or notice.
BlocksP3, where share, fetch and Arrow exports are built.
ProposedA licence-propagation ADR: each pack table carries the set of sources it derives from; share sends the scenario file and hashes only, and the recipient rebuilds from their own pack; exports embed the attribution text and refuse no-redistribution tables. Card 3.
5Failure handling: halts, panics, repro bundles
Found4.6 says an invariant violation halts the run, and the core panics on bad inputs (geo SPEC radius check, ledger overflow). Nothing says what the app does then: lose the session, show the tick and invariant, offer to fork back? Nothing defines a panic-versus-Result boundary between core and app, logging levels, or where logs go.
BlocksApp shell (the first build a non-developer opens) and P3 (fuzzing in 0120 already shrinks failures to a minimal manifest).
ProposedA failure ADR: the core returns a typed halt (tick, system, invariant, values) and the app keeps the last snapshot, shows the halt, and writes a repro bundle (scenario file, pack hash, engine version, tick) that replays the failure exactly on any machine. Determinism makes this unusually strong; most games cannot reproduce a crash at all.
6Slint licence in CI and the About screen
Founddeny.toml allows only permissive licences and the migration plan says "No GPL/AGPL". Slint is published as GPL-3.0 or its royalty-free licence or commercial; the royalty-free one is a LicenseRef that the allowlist does not name, so cargo deny check licenses should fail the day Slint enters the workspace. 0088 also requires the AboutSlint widget in an About screen, which no ADR places.
BlocksApp shell CI.
ProposedAdd a deny.toml exception for Slint's royalty-free licence in the App shell's first PR, and put the About screen into #9. No ADR needed.

7First-run data fetch and source durability
Foundfetch.toml pins 50 files, about 6 GB, by sha256; 13 are manual downloads from three providers (OECD ICIO, Global Energy Monitor, Kummu GDP). The README still says 920 MB. When a provider revises or removes a pinned file, every new user is blocked and the R gate ("a clean machine reproduces the published hashes") fails. There is no mirror policy, no design for guiding a manual download, resuming, disk checks, or rebuilding the pack when an app update changes the schema.
ProposedA first-run ADR: an in-app fetch screen per source (size, licence, status, a drop zone for manual files checked by hash), resumable downloads, and an archive of each release's redistributable sources on Zenodo, with upstream used for the rest. Card 4.
8Platforms, signing, updates, minimum Mac
FoundR says "a signed macOS build". 0128 wants the golden hash on macOS, Linux and Windows. Undecided: whether 1.0 ships a Linux CLI, the Apple Developer account (99 USD a year on a non-commercial project), the channel (GitHub Releases, Homebrew cask), how updates reach users, and what happens on a 16 GB Mac when 19.2 assumes 18 to 36 GB.
ProposedA distribution ADR. Suggested defaults: macOS app plus a headless CLI for macOS and Linux (CI already runs Linux), GitHub Releases and a Homebrew cask, an update check that only notifies, and a 16 GB minimum with fewer lanes and a longer history interval.
9Attribution UI and the meaning of "release profile"
FoundCC BY sources need credit where the data is shown; IFPRI asks for a set sentence on adaptations; ODbL needs a notice; Slint needs its About widget. No screen holds these. ADR 0050 still builds the release profile on commercial_use and cites a Steam plan, both overtaken by the 28 October decision: with user-side fetch the real split is what may ship prebuilt (tiles, from redistributable sources) and what each user fetches.
ProposedAmend 0050 so the profiles mean prebuilt and user-fetched, and generate a Credits and licences screen and the export notices from sources.toml.
10Telemetry and crash reports
FoundNo mention anywhere.
ProposedState a stance in the failure ADR (#5). Card 5.
11Opening the repo and taking contributions
FoundThe project is "open source", but the repo has no CONTRIBUTING, code of conduct, security policy, issue templates, or rule on DCO versus CLA; 0088 speaks of "when the code opens" without a date. 22.1 asks for a name check on crates.io and GitHub that nothing records as done. With one part-time maintainer from February 2027, review load is the binding cost.
ProposedA governance ADR with the files it implies. Card 6.
12Documentation set
Found15.7 requires an ODD-protocol model description "so outsiders can review it"; no phase owns it. R ships a minimum pedia (0158). There is no user manual, no methods page behind the scorecard, and no developer guide beyond CLAUDE.md.
ProposedPut the ODD description into P9 next to the scorecard, generated in part from SPEC files and the register (17); the user guide grows from 0158's pedia in R. Agent default.
13Localization pipeline and 1.0 languages
Found0078, 0140, 0143 and 0158 assume Fluent files and refer to "every game language", which no ADR defines. Number, date and currency formats, CJK and right-to-left fonts in Slint, and the translation workflow are open.
ProposedEnglish only in 1.0, with every user-facing string in Fluent from the App shell on, so adding a language later is translation work, not refactoring. Agent default unless you object.
14Colour-vision-safe map modes and UI scale
FoundCovered: keyboard-only use and screen-reader names through AccessKit (0188), reduced motion (0137), WCAG AA chrome (0140). Missing: palettes for the map modes that read under the common colour-vision deficiencies, difference maps whose robustness mask (14.5) is not carried by colour alone, and a UI scale setting.
ProposedAmend 0137: every ramp passes a CVD simulation check in CI, the mask uses hatching, and a UI scale from 85% to 150%.
15Disputed borders and sensitive-content stance
Found0006 keeps Natural Earth's de facto assignment for everything not listed in borders_2000.toml (Kashmir, Western Sahara, Taiwan's status, Abkhazia and others). The choice is reasonable but undocumented to users, and Natural Earth also ships per-country point-of-view layers. 22's risk table promises neutral modelling and no editorial text, with no policy behind it.
ProposedAn ADR that states the de facto rule, lists disputed areas in the pedia with each claimant's view, and leaves worldview switching to a data mod.
16Long-horizon and app testing
FoundWell covered: goldens, proptest, the nightly self-hosted pack gate (pre-P3 D5), fuzzing (0120), cross-platform hashes (0128). Open: where the 100-year and 2150 runs on the full pack execute and how long they may take, any test of the Slint app (screenshot or interaction), and a CI job that builds the pack the way a user does.
ProposedTasks in the App shell and R plans; no ADR.

1. Who sets policy in 1.0, after the tape ends?

Recommended: estimated rules per lever, fed by the tape to 2024

2. What happens when a new version opens an old run?

Recommended: stored results read-only, re-simulate as a labelled branch

3. What does sharing a run send?

Recommended: the scenario file and hashes only

4. How do pinned sources survive provider changes?

Recommended: archive redistributable sources on Zenodo each release

5. Telemetry and crash reports

Recommended: none; a local repro bundle the user can attach to an issue

6. When does the repo open, and on what terms?

Recommended: public now, issues open, code contributions after 1.0 under DCO

Recommended: the five gate blockers, as 0210 onward
